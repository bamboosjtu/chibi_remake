# 16 存档与兼容

> 本章定义存档槽、文件结构、写入协议、校验与版本迁移。存档触发点见[游戏流程](02-game-flow.md)；数据字段见[数据规格](15-data-spec.md)。

## 1. 槽位

| 槽 | 文件 | 用途 |
|---:|---|---|
| 0 | `save.json` | 自动槽：结束战役、关闭窗口；兼容旧版单档 |
| 1–20 | `slot-01.json` … `slot-20.json` | 手动槽：玩家命名保存 |

- 每个槽独立保存，覆盖一个槽不影响其他槽。
- 槽列表显示：名称、关卡、保存时间；损坏记录置灰不可读。
- 手动槽名称最长 40 字；留空时使用关卡名。

## 2. 位置

绿色发行物以 `portable.txt` 显式选择本地存储：独立候选使用 EXE 旁 `userdata/<用户名>`，启动器显式传入发行根的 `userdata`，跨版本保持位置稳定。移除配置或使用 `--storage-mode=system` 可选择系统存储。

系统模式优先保留已有槽位所在目录；首存逐个尝试并实际写入验证：

1. `%LOCALAPPDATA%/ChibiRTS/saves/`
2. `%APPDATA%/ChibiRTS/saves/`
3. Godot 用户数据目录
显式使用 `--portable` 或可执行文件旁的 `portable.txt` 时，优先使用可执行文件旁的 `userdata/<用户名>/`；默认模式不探测该位置。

- 启动选择路径不创建空存档目录；实际提交创建最终目录、写入并回读临时文件，通过后才认定可写。已有槽位或显式便携根不静默切换。失败记录目录、目标槽文件、临时文件、阶段及错误码，保留旧档并清理本次临时文件。
- 旧位置的有效存档会迁移到新位置；已存在的新档不被旧档覆盖。
- 启动日志与保存提示会给出实际路径。
- 每个槽保留一个 `.bak` 备份。

## 3. 文件结构

```json
{
  "v": 8,
  "kind": "save",
  "map": "chibic1",
  "saveName": "赤壁首战",
  "savedAt": "YYYY-MM-DDTHH:MM:SS",
  "nextUid": 120,
  "gameEnd": 0,
  "resources": { "gold": 3000.0, "wood": 2000.0, "food": 1000.0, "stone": 800.0 },
  "units": [ ... ],
  "trainings": [ ... ],
  "simulation": { ... },
  "checksum": "<SHA-256>"
}
```

### 3.1 单位记录

| 字段 | 说明 |
|---|---|
| `uid` | 稳定 UID |
| `alive` | 是否存活（含淡出中的尸体标记） |
| `x` / `y` | 脚点像素 |
| `hp` | 当前生命 |
| `owner` / `unit` | 归属与类型 |
| `building` | 是否建筑 |
| `mapObject` / `mapIndex` | 是否地图对象及其序号 |
| `dieT` | 死亡淡出进度，−1 表示未死亡 |
| `state` | 当前状态名 |
| `officerIndex` | 所辖武将索引，−1 表示无 |
| `simulation` | 模拟字段（见 3.2） |

### 3.2 模拟字段

单位级字段包括：

- 位置与朝向：`A`、`B`、`dir`、`pi`、`path`；
- 生命与加成：`maxhp`、`base_maxhp`、`tech_hp_bonus`；
- 动作：`action_wait`、`action_phase`、`action_started`、`action_kind`、`action_target_uid`；
- 计时：`rest_t`、`build_t`、`gather_t`、`gather_ticks`、`delivery_ticks`；
- 状态计时：`inspired_t`、`haste_t`、`slow_t`、`farsight_t`、`confused_t`、`ambush_t`、`rolling_t`；`hidden_t` 仅作为旧档别名读取；
- 采集与载货：`carry`、`carry_kind`、`gatherRef`、`stock`、`stock_max`；
- 施工：`site`、`site_inside_uid`、`site_follow_uid`、`site_entry_x/y`、`site_exit_pending`、`build_cost`；
- 运输：`attached`、`aboard_uid`、`carry_n`、`carry_hp`、`loaded`、`unload_active`、`unload_t`；
- 编组与目标：`group_officer`、`join_target_uid`、`targetUid`、`build_targetUid`、`repair_targetUid`、`board_targetUid`；
- 其他：`hold`、`cool`、`repath`、`anim`、`moved`、`build_frame`、`status_173`、`mou`、`formation`、`fo_x/y`、`exp` 相关字段。

引用字段一律保存 UID 或稳定键，不保存对象：

- 采集目标：`{"kind":"decor","cell":"A_B"}`、`{"kind":"unit","uid":N}` 或 `{"kind":"spent","unit":N,"x":..,"y":..}`；
- 施工/修理/上船目标：对应 `*Uid`；
- 攻击目标：`targetUid`。

### 3.3 全局模拟

| 字段 | 说明 |
|---|---|
| `contentRevision` | 关卡有效定义的规范哈希，包含水层及资源布置（见 15 章） |
| `rulesRevision` / `rulesPolicy` | 独立规则版本及兼容策略；新档要求规则版本完全匹配 |
| `tick` / `accumulator` | 已走 tick 与余量 |
| `speedIndex` | 速度档位 0–3 |
| `autoControl` | 可选布尔值；托管开启时写入 `true`，缺省为关闭；无效类型在构建候选世界前拒收 |
| `explored` | 迷雾探索位图（Base64） |
| `projectiles` | 飞行中的箭/石 |
| `decorResources` | 饰物剩余存量 |
| `aiResources` | 各势力四资源 |
| `groups` | 控制组（组号 → UID 数组） |
| `taskLatches` | 任务阶段锁存 |
| `taskEvents` | 已触发事件游标 |
| `officerProgress` | 任务事件经验 |
| `terrainChanges` | 地形清除记录 |
| `objectiveDone` | 脚本目标是否达成 |
| `officerPool` | 武将池经验/等级 |
| `playerTech` / `armyTech` | 玩家与各势力科技等级 |
| `techProgress` / `researchJobs` | 旧式单项研究/建筑研究订单 |
| `rngState` | 战斗随机数状态（十进制字符串） |
| `fireFields` | 单格火场列表（坐标、存在时长、归属） |
| `ai` | AI 计数、计划、撤退、陆军槽、水军槽 |

### 3.4 生产订单

| 字段 | 说明 |
|---|---|
| `buildingUid` | 生产建筑 UID |
| `unit` | 兵种 |
| `t` | 剩余 tick |
| `ticks` | 是否 tick 计时 |
| `owner` | 订单归属（独立于建筑当前归属） |
| `cost` | 已支付费用 |
| `aiSlot` / `aiToken` | 陆军槽关联 |
| `navalSlot` / `navalToken` | 水军槽关联 |

武将池的 `hasExp` 可选布尔字段保留经验键是否存在；旧档没有该字段时按既有经验恢复规则处理。字段缺失与显式零在成长计算中等价，但完整恢复保留两者在规范摘要中的区别。

## 4. 写入协议

1. 序列化为带缩进的 JSON；
2. 写入唯一临时文件；
3. flush 后重新解析并校验；
4. 当前主文件通过结构与 checksum 校验时才轮换 `.bak`；损坏主档及无 checksum 的旧档隔离为 `.damaged-*`，保留已有的已验证备份；
5. 临时文件改名为正式文件；
6. 读回校验；失败则回滚到 `.bak` 或隔离文件。

- 任一阶段失败都保留上一份有效存档。
- 备份不会因一次无效主文件被覆盖。
- 保存失败时返回原因（阶段与错误码），界面提示并保留原记录。

## 5. 校验和

- 覆盖除 `checksum` 外的整个 payload。
- 规范化：键排序、整数按整数输出、浮点保留 6 位小数、非有限值写 `null`。
- SHA-256 十六进制存入 `checksum`。
- checksum 校验只判断校验和存在且匹配；缺失时返回失败。
- 文件有效性另外检查版本、关卡标识、单位记录及基础字段结构；只有结构合法的 v1–v7 档可走无 checksum 的兼容读取路径。
- v8 必须显式包含 `resources`，且 `gold/wood/food/stone` 四键全部为有限非负数；必须显式包含 Array 类型的 `trainings`，空队列须写为 `[]`。缺字段不能通过默认值补齐。文件读取、内存快照应用和候选恢复共用该版本策略。
- v1–v7 保留缺省兼容：缺生产队列表示没有生产，缺资源键沿用旧版恢复种子值（v1–v3 来自地图，v4–v7 来自候选输入）。生产/研究的费用字典仍可只列实际支付的资源，不能与玩家资源快照的完整性混用。
- 无 checksum 的旧档可以加载，但不能替换已验证的备份。文件有效性不代表与当前关卡/规则兼容，完整语义校验仍在创建候选前执行。

## 6. 加载流程

1. 读取文件并检查结构与 checksum（或受限的旧档策略）；主文件无效时读 `.bak`。
2. 校验 `map` 与当前关卡一致。
3. 校验 `v`：大于当前版本拒绝；v4–v8 走当前路径；v1–v3 走兼容路径。
4. 校验关卡定义和独立规则版本。无规则指纹的旧档可按已登记结构迁移采用当前规则；有指纹的档案必须规则匹配，不能用兼容表绕过规则版本拒收。
5. 在**修改世界之前**完成全部结构校验：
   - 单位 UID 唯一且在已登记整数范围内、类型/归属/图集有效；building 若存在必须与 unit 派生分类一致；
   - v4–v8 路径点、坐标有限且转换为 Vector2 后仍有限；格位/游标按已登记类型校验，完整地图边界与游标关系尚未统一覆盖；
   - 资源、击杀者 UID、采集引用、施工/修理/上船引用合法；
   - 生产订单：建筑存在、订单归属合法、无重复、费用合法（归属独立保存，保留旧档跨势力生产约定）；
   - 研究订单：建筑存在、同属、科技与线匹配、无重复；
   - 计时与动作字段为整数且在范围内；
   - 生命上限满足“基础 + 科技加成”契约；
   - 载员图：人数 ≤ 16、船/载员归属一致、汇总与真实成员一致；
   - 弹体、地形变化、AI 槽位、控制组结构合法。
6. 校验通过后交换世界：生成实体、写回 UID、解析引用、恢复资源/科技/任务/AI、重建导航与城门、恢复视野。
7. 同步表现：隐藏载员、刷新面板、清空旧的待选命令。

失败时原世界、选择与载入状态保持不变，并给玩家可读原因。

## 7. 版本迁移

| 来源 | 处理 |
|---|---|
| v1 | 4 字段数组，按下标配对；仅恢复位置/生命 |
| v2 | 10 字段数组，带 UID 与身份 |
| v3 | 具名字段，完整实体快照；缺席实体全部移除，含动态单位和建筑 |
| v4 | 增加全局模拟字段；缺失秒值按 1/30 秒换算 |
| v5 | 计时字段仍为秒；迁移到 tick |
| v6 | 休息/施工/六状态改为整数 tick；新增科技/研究订单 |
| v7 | 新增动作相位、弹体、AI 陆军槽 |
| v8 | 新增载员身份图、卸载相位、AI 水军槽、探索 |

迁移原则：

- 旧秒值按 `1/30` 秒换算为 tick；缺字段置 0。
- 缺 `armyTech` 时非玩家势力回到未研究。
- 缺载员字段时按真实成员重算汇总；隐藏的死亡载员清除船引用。
- 旧槽位/订单缺失时清空对应槽，不猜成普通订单。
- 超过 15 名成员的旧队按 UID 保留前 15 名，超额成员解除编组并保留生命与载货。
- 旧动作相位无法推断时从命令首 tick 重新初始化。

## 8. 兼容边界

| 情况 | 结果 |
|---|---|
| 关卡定义变化 | 无明确迁移时拒绝，保留原档 |
| 已带指纹的规则版本变化 | 仅接受指纹完全匹配或明确批准的迁移；其余拒绝并保留原档与当前战场 |
| 内容哈希命中兼容表 | 允许加载 |
| 未知字段 | 忽略，不报错 |
| 非法字段值 | 拒绝加载 |
| 版本高于当前 | 拒绝加载 |
| 关卡文件已删除 | 拒绝并从关卡列表提示 |
| 图集/纹理变化 | 不影响存档 |

## 10. 验收要点

- 保存失败不破坏旧档；损坏主档不覆盖有效备份。
- 读取失败不修改当前世界，选择与载入状态保留。
- 同状态存读后继续相同 tick 数，结果与不读档一致。
- 非法载员、负 UID、越界计时、重复订单在交换世界前被拒绝。
- 上升级后上船、船内升级、受伤后登船等合法状态可存读。
- 跨关卡读取会切换场景并在新场景内恢复。

实时导航优化保留 v8 格式，新增可选 `route_failures`（整数 0–3）与已有 `repath` 一起保存；旧档缺省为 0。接敌路径失败采用 0.8/1.6/3.2 秒退避，并按稳定 UID 分散重试时点，显式新命令清除退避状态。延迟按模拟时间推进，存读不重新计时。

`rules_contract.json` 中的 `realtime-navigation-v1` 只批准 `d483478` 与 `05d3a2e` 的两个确切规则指纹迁移到此次确切目标指纹：保留存档状态、引用、计时和经验，采用新的路径与重试行为。未批准的其他规则或未来版本仍被拒收；该项不会自动为后续平衡变化放行。缓存、渲染队列、GPU 纹理和性能计数器均不写入存档，恢复时按新世界重建。


计算后端更换不升级 v8 格式。`05d3a2e` 的规则指纹明确迁移到经过脚本/原生完整状态对照的当前指纹；该许可不会推广到任意未来规则。坐标、接触、导航预热与视野缓存由新世界重建，原生提供者不保留旧世界引用；音效分组、主题布局缓存和剖析数据均不进入玩家快照。规则身份由显式规则 ABI 与模拟数据投影构成。代码行为变化须复审 ABI 和确定性基线；源码清单、原生源码签名与 DLL 字节分别用于构建完整性校验，均不自动混入玩家存档的规则指纹。


## 11. 规则身份的输入边界

`rules_identity.gd::CATALOG_FIELDS` 显式列出单位、生产、建筑、状态调参、武将、等级奖励、命令能力和战役规则。投影排除来源说明、显示名称、图集位置、素材路径和施工帧；动作/死亡帧保留长度，因为长度参与动作节拍。地图内容版本继续单独检查。

小地图、音频、视频、UI 布局、引擎哈希、注释和构建源码清单不参与规则指纹。模拟规则代码变化通过 ABI 评审管理，不能仅更新源码清单而省略规则兼容性评审。`rules-scope-v1` 仅把已登记的旧宽指纹迁移到确定的新目标；后续调平衡数据后，许可自动失效，需要重新评审。

记录组的线格式键由 `UnitSchema.record_value` 提供给恢复器，位置、生命、死亡和武将身份的语义仍由 SaveService 处理。逐字段测试通过真实候选恢复验证全部 record 字段，并拒绝每个字段的错误类型；恢复不能只验证标量组。

`battle-rules-v4` 明确采用分批堵塞重寻路。可选标量 blocked_cursor 的范围为 0–48，记录当前终点邻域搜索的位置；成功移动、取消命令或一轮搜索结束后删除。v8 旧档缺少该字段时从零开始，新档经 Schema 保存、校验和恢复中途进度。注册在 rules_contract 中的旧指纹只迁移到固定的 v4 目标，策略名为 bounded-blocked-navigation-v1；其余未知指纹继续拒绝。该迁移采用新重试时序，保留其他单位状态、计时器和资源。资源片、点击桶及决策索引全部重新构造，不作为存档数据。


## 存档语义的已实施边界

终局值 gameEnd 为整数 0（进行中）、1（胜利）、2（失败）。v4–v8 的 nextUid 必须在 0–2147483647 范围内；恢复仍会根据实体最大 UID 补足计数器，不把低于现存最大 UID 的旧计数器当作身份冲突。UID、unit、owner 在转换为整数前按 Schema 检查数值范围，避免过大浮点输入在转换阶段产生异常。

记录中的 building 必须与统一的兵种分类谓词一致，不能把移动单位标成建筑通过队列校验。state 只接受当前状态目录，包含运输中的 boarded。未知状态及无法表示为有限 Vector2 的巨大坐标/路径点会被拒绝，失败不交换当前世界。

地图相关准入由 SnapshotSemantics 统一执行。单位锚点、路径、重寻路点、施工入口和 spent 资源点必须是有限 Vector2，且位于画布加一格 tileW 的兼容边缘内；超出该边缘拒绝。恢复时将边缘内的画布外点夹回有效画布。v1–v3 的位置也执行同一准入；合法旧档的数字布尔值 0/1 继续支持。地图判定在候选恢复前完成，失败保留当前世界。

路径最多 rows×cols+2 个点，对应简单 A* 路径及起止补点。pi 必须是非负 32 位整数，缺省或旧 null 按 0 处理。空路径遗留的非零游标、非空路径中等于或超过长度的游标属于旧执行器的清理窗口：序列化与恢复共用 Schema 的规范化，将其变为空路径和游标 0，不修改传入快照。A/B 属于 cell_cache 派生组，新档不写出；旧档中类型合法的缓存值忽略，按恢复位置重算。

Schema 在整数转换前统一限定有符号 32 位范围，各字段的更窄约束继续生效。rngState 独立使用有符号 64 位十进制字符串，tick 非负、speedIndex 为 0–3、accumulator 有限且非负；这些时钟规则也参与文件有效性检查。

稳定引用的兼容规则为：build/repair/board 目标必须存在或为 -1；targetUid、join_target_uid 和 gatherRef.unit 可以处于目标刚被清理的窗口。恢复将悬空对象引用变为 null、悬空加入 UID 变为 -1，保留当前命令供执行器正常清理。last_attacker_uid 和 action_target_uid 是历史/时钟身份标记，不强制仍有存活对象，但数值类型和范围受 Schema 约束。spent 资源仍保存种类与有界原位置。未知引用编码拒绝。

taskLatches/taskEvents 各最多 4096 项，两个子树合计最多 32768 个值节点、深度最多 8；键最长 256 字符，字符串值最长 65536 字符。事件必须有非负整数 id，可省略 tick（缺省 0）；未知数值事件 ID 和有界扩展字段保留，以兼容旧历史与后续目录。费用允许缺少零成本资源键，但只接受 gold/wood/food/stone 及有限非负数值；存档、施工成本和恢复器共用 ResourceCost 定义。

JsonStore 在 JSON 解析前限制文件为 32 MiB、容器深度为 64，字符串内的括号和转义不计深度；提交也执行相同限制。文件校验能证明结构、checksum 和与地图无关的约束，不代替候选中的地图/规则兼容性校验，也不证明路径在当前地形上可走。

SaveRepository.read_slot 返回 data 和 source（primary、backup、none），旧 load_slot/read 接口仍返回数据本身。槽位缓存以文件长度、修改时间和 SHA-256 判定变化，覆盖同大小、同修改时间的外部损坏；超限文件不做全文哈希。列表和读取提示明确标注使用备份，实际读档来源记录在 SaveService.last_load_source。恢复后的生产费用、AI 资源池和旧研究费用由新世界拥有，修改输入快照不会修改这些容器。
