# 原版《赤壁》人口/实体上限分析

> 目标版本：`CB.EXE` SHA-256 `2db7cc102e6fde547ab05d77cfddabc2079f5bc9be9b6b59b17bf435c5798cb7`。  
> 仅以原版 `CB.EXE` 静态反编译为准；`docs/` 与重制实现只用于对照。

## 0. 结论速览

- **在原版静态代码中没有发现独立的“人口值”资源，也没有住房/人口建筑**；所谓人口上限本质上是**每方固定 200 个实体槽位**，玩家和电脑共用同一套上限。
- 每个 side 有 **200 个实体记录槽位**（索引 0–199）；部队、工人、武将本体、建筑都占用同一套实体槽位。
- 另有一套 **20 个武将槽位/每方**，即一方最多同时存在 **20 名武将**；武将本体同时占用一个实体槽位和一个武将槽位。
- 粮食上限是**资源容量**，不是人口：每座已建成帅帐/大本营或粮仓提供 **10000 粮容**；公式见 `FUN_004262F0`。
- 静态代码中**没有发现“每个单位消耗人口/粮食维持费”的人口上限逻辑**；训练费用四资源仍然存在，但不影响实体槽位。
- 代码分配器有一个边界细节：实体槽数组是 200 个，但 `FUN_00459e20` 的扫描循环是 `uVar7 < 199`；满员边缘可能提前返回 `No room`。因此可以表述为：**设计/数组上限 200，实际分配器存在 199 次扫描的边界行为**。
- 生产和建造不是先占一个永久人口名额再出生：原版是在实际创建实体时由 `FUN_00459e20` 分配槽位；分配失败时报错。未出生订单是否预占槽位，未在 `DAT_004b8d38` 的原版检查路径中发现明确实现。

## 1. 每方 200 个实体槽位

### 1.1 实体记录数组

原版每个 side 的单位记录基址为：

```text
DAT_004b8d3c + side * 0x12358 + index * 0x174
```

- `index`：实体槽索引；
- 每条记录 `0x174` 字节；
- 索引范围：**0–199**，即每方 200 条记录；
- 每方独立的 `DAT_004b8d38[side]` 记录当前活跃实体数；
- `FUN_0045AFE0` 的统计循环，以 `< 200` 扫描每个 side 的实体槽。

### 1.2 分配与释放

关键函数：

- `FUN_00442970`：通用实体创建；
- `FUN_00459e20`：在 per-side 数组中寻找空槽并初始化实体；
- `FUN_00459d70`：释放/清除实体记录。

`FUN_00459e20` 的关键行为：

```text
从 DAT_004b8d3a[side] 开始寻找空槽；
找到空槽后：
  DAT_004b8d38[side] += 1
  返回带 side/槽号的实体句柄
找不到空槽：
  OutputDebugStringA("MAP_SetUnitData_Error_1___No_room")
  返回 0xffff
```

`FUN_00459d70` 在实体清除时把 `DAT_004b8d38[side]` 减 1。

### 1.3 200 个槽位包含哪些东西

- 普通战斗单位；
- 工人；
- 武将本体（额外占用一个实体槽）；
- 建筑（建筑也是实体记录；因此建筑会占人口槽位）；
- 舰队/运输船等可移动单位；
- 地图初始对象中的单位/建筑也会先消耗对应 side 的实体槽位。

因此“200 人口”不是“200 个战斗兵”，而是**200 个实体**。如果一方建了很多建筑，可用于战斗单位的空槽会相应减少。

### 1.4 分配器的 199 次扫描边界

`FUN_00459e20` 的循环条件为：

```c
do {
  ...
  uVar7 = uVar7 + 1;
} while (uVar7 < 199);
```

即虽然有 200 个槽位，但一次寻找最多只检查 **199 个候选槽**。这意味着：

- 正常情况下可以把它描述为“200 实体上限”；
- 在极端满员情况下，如果唯一空槽刚好落在扫描范围之外，原版可能提前报 `No room`；
- 这是原版分配器的边界行为，不要把它和“设计上限 200”混成两个互斥结论。

## 2. 武将上限：每方 20 名

`FUN_00442E40` 在创建武将/队伍时扫描武将槽数组：

```c
do {
  if (*psVar6 == -1) {
    local_1c[0] = 1;
    ... 占用武将槽 ...
    break;
  }
  psVar6 = psVar6 + 1;
  iVar5 = iVar5 + 1;
} while (iVar5 < 0x14);     // 0x14 = 20
```

结论：

- 每个 side 有 **20 个武将槽**；
- 没有空武将槽时，武将创建失败；
- 武将本体另外占用一个普通实体槽，所以“20 名武将”不是额外的 20 人口，而是 200 个实体中的 20 个（且受 20 个武将槽限制）。

## 3. 粮容不是人口上限

### 3.1 粮容公式

原版粮容由 `FUN_004262F0` 读取：

```c
return DAT_004b8d34[side] * 10000 <= DAT_004b8cfc[side];
```

其中：

- `DAT_004b8d34[side]`：该方已建成的帅帐/大本营和粮仓数量；
- `DAT_004b8cfc[side]`：当前粮食；
- 每座建筑提供 **10000** 粮容；
- 交付粮食超过容量时，`FUN_00421B50` 报 `Food Exceeded` 并撤销本次增加。

### 3.2 为什么它不是人口

- 粮容只限制**粮食库存**；
- 不限制单位数量；
- 不要求每名单位消耗粮食；
- 没有“人口房屋”或“农场提供人口”的系统；
- 帅帐/粮仓也是实体，占 200 实体槽位，但它们增加的是粮容，不是人口上限。

## 4. 生产订单与上限

从原版代码可确认的路径是：

1. 训练/建造完成并实际创建实体时调用 `FUN_00442970`；
2. `FUN_00442970` 调用 `FUN_00459e20` 分配实体槽；
3. 若无空槽，创建失败并输出 `No room`。

在原版 `DAT_004b8d38` 的引用中，没有发现训练订单在入队时直接检查 `< 200`、并把未出生订单永久计入实体槽的代码。  
因此本文不把“订单预占 200 实体上限”写成原版结论；订单系统是否在 UI/生产层另有排队限制，需要按生产命令路径单独核对。

## 5. 对照重制/文档时要避免的混淆

- `docs/01-overview.md` 的“每方 200 个实体、武将不超过 20 名”与原版代码方向一致，但文档不是原版证据。
- `docs/03-economy.md` 的粮食上限 `(大本营 + 粮仓) × 10000` 与 `FUN_004262F0` 一致；它是粮容，不是人口。
- `docs/05-production-tech.md` 的“未出生订单计入 200 实体上限”属于重制规则描述；原版实际槽位分配点在 `FUN_00459e20`，不要直接把重制的订单预占当作原版行为。

## 7. 局限

- 本文为静态代码分析；没有运行原版逐帧验证 200 槽满员时的实际 UI 提示与订单行为。
- `FUN_00459e20` 的 199 次扫描是原版代码边界；实际玩家在正常对局中是否容易触发该 off-by-one，取决于槽位游标和空槽位置。
- 建筑是否在同一时刻全部计入实体槽由实体创建路径决定；地图初始建筑/单位也占用槽位，本文按“实体记录”统计。
- 不同版本或重制版的订单预占、建筑不占人口等规则可能不同；本文不把重制行为混入原版结论。
