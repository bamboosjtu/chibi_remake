# 《赤壁》原版：每关开局阵位与电脑进攻机制

> 研究对象：`CB.EXE` SHA-256 `2db7cc102e6fde547ab05d77cfddabc2079f5bc9be9b6b59b17bf435c5798cb7`。  
> 仅以原版二进制与 `SET/*.EXP`、地图数据为准；未由原版证明的内容不写成原版规则（未决项见 `research/todo/README.md`）。
> 地图对象来自 `godot/chibi_remake/data/*.json` 的原版 MED 转换；AI 计时、等待、目标选择全部由原版反编译确认。可视化入口：`index.html`。

## 1. 结论摘要

- **34 关、39 个电脑方**。每关 `scenario.sides[0]` 是我方，其余 side 都是电脑；多电脑关卡的电脑之间不结盟、不互相攻击，只把玩家方作为目标。
- 我方开局共 **93 个编组、726 个成员单位**（武将本体另计）；敌方开局共 **2051 个成员单位**（不含武将本体和中立 0 方）。
- **武将本体不单独放在地图对象里**：地图中同一 `tail[0]` 的全部部队都是该武将的成员；武将在**首成员格**另生成，和首成员同格，不占地图对象、不计入成员数。本文成员偏移都以首成员为 `(0,0)`，`A` 向右、`B` 向下。
- 电脑进攻是**按 side 独立计时**的：AI 每 **41 次主更新**思考一次；默认进攻阈值 **70**，即每 **71 次 AI 思考**检查一次。玩家可见实体 `<6` 时，要在**当前一轮达到阈值后**才把阈值改为 **6**；首轮不会倒推缩短（后续每 7 次思考）。
- 进攻前还有**等待门槛**：`DAT_004b8d29[AI] < AI init[1]` 且 `(DAT_004b8d29[玩家] < 玩家 init[1]−1 或 玩家金 <15000)` 时，本次不进攻，计数归零；等条件解除后重新累计。`DAT_004b8d29` 是 **0 基**的升级等级字节（0 = 未升级，没有帅帐的一方也是 0），不是界面上的 1–4 级：`FUN_00422330` 的三个大本营升级 case 直接写死 `mov byte [侧+0x4B8D29], 1 / 2 / 3`（升二级/三级/四级），所以开局必然为 0。`chibil14`（missionId=0x0e）是代码中显式绕过该等待的特殊关。
- 目标选择**不是最近单位**：`FUN_00464B40` / `FUN_00464C90(4)` 按玩家单位槽顺序扫描，取第一个符合类型/状态的目标。英雄类与普通类 AI 单位使用不同筛选函数。
- 34 关开局玩家对象数（含建筑）都 ≥6，因此第一轮进攻阈值均为 **70**（开局触发 6 阈值的电脑方：0 个）；玩家实体被打到 <6 后，仍在**下一轮达到当前阈值时**才把阈值改为 6。存在门槛等待的电脑方在开局会先等待，所以首波实际时间通常晚于理想值 2911 次主更新。
- `init[0]` 是**训练/建造行为档位**，不是进攻阈值；`init[1]` 是科技门槛；`init[2]` 是信息面板变体标志（当前界面不区分）。

## 2. 数据口径与坐标

### 2.1 地图对象

- 每关地图的 `objects[]` 中，可编组部队类型为 27、28、30、32、34、36–46、48、49。
- `A/B` 是原版地图格；`px/py` 是按原版渲染公式得到的屏幕像素：`px = 44A + 22(B&1) + 22 − w/2`，`py = 11B + 22 − h`。
- `tail[0]` 为统辖武将编号（0 表示不编组）。`scenario.roster` 中的编号与 `tail[0]` 对应；`research/20-units/data/heroes.json` 的 `index = tail−1` 给出武将名。
- `objects` 的顺序与原版生成顺序一致；同一武将的首支部队作为武将本体位置。文献中的“主将”在本包里指该武将，而不是另生成的一张独立地图对象。`levels.json` 中每名士兵还带 `dpx/dpy`（屏幕像素偏移），便于还原像素位置。

### 2.2 来源与可复现性

- 地图场景/对象：`godot/chibi_remake/data/<map>.json`，由原版 `MEDS/*.MED` 转换；对象 A/B 与 px/py 保留。每个关卡的实际 MED SHA-256 见 `data/levels.json` 的 `source.medHashes`。
- 机器可读数据：`data/levels.json`（逐单位/逐电脑）、`data/ai_sides.csv`（39 个电脑方一行）、`data/levels.csv`（逐我方编组）。
- AI 代码：原版 `CB.EXE` 的 Ghidra 反编译；关键函数与地址见第 7 节。
- 重跑：

```bash
node research/60-ai/tools/extract_ai.mjs
```

## 5. 电脑进攻机制：代码层拆解

### 5.1 谁被当作电脑、谁被当作目标

- `FUN_0045AFE0` 遍历每个 side；`DAT_004b8cb4[side] == 2` 的 side 进入 `FUN_00472320`，即电脑方。
- `FUN_00472320` 的第二参数是当前关卡号 `DAT_004b8b6c`（不是 side）；它把当前 AI 的门槛/行为档位写入 `DAT_005d1e00[missionId]` / `DAT_005d2ee8[missionId]`，然后调用 `FUN_00472230(aiSide, missionId)`。
- AI 的所有目标扫描都读 `DAT_004b8cac`（玩家方）；代码中没有 AI 对 AI 的攻击分支。多电脑关卡因此是“所有电脑各自打玩家”，不是混战。

### 5.2 思考节拍

- `FUN_00472320`：`DAT_00485648[side]` 从 0 开始，`<0x28` 时自增；达到 `0x28`（40）后归零并执行 `FUN_00472230`。因此一个完整周期是 **41 次主更新**。
- `FUN_00472230` 的顺序（代码 0x00472230 附近）：
  1. AI 金置为 **20000**；
  2. `FUN_0046AFF0` 按行为档位训练；
  3. 每 **22 次 AI 思考**刷新一次建造/研究计划（`FUN_0046E4B0` / `FUN_00470570`）；
  4. `FUN_00471600` 进攻检查；
  5. `FUN_00471B30` 撤退/回城检查；
  6. `FUN_00471FD0` 局部拦截/自动攻击；
  7. `FUN_00472180` 生产槽/后勤状态更新。
- 因此电脑的进攻不是“每关写死的波次”，而是同一套运行期状态机；关卡数据主要改变初始兵力、行为档位、科技门槛和地图位置。

### 5.3 进攻计时与开局首波

- 默认阈值来自初始化：`FUN_0046A180` 把 `u_FFFFF_00485668[side]` 设为 `0x46 = 70`。
- `FUN_00471600` 先比较并自增 `DAT_00485638[side]`；达到阈值后归零并检查等待条件。
- 触发周期：计数从 0 到 70 后才执行，因此是 **71 次 AI 思考**；`71 × 41 = 2911` 次主更新（未等待、无其他中断时）。触发后计数归零，后续没有门槛时仍按同一节拍重复。
- 玩家可见实体 `DAT_004b8d38[player] < 6` 时，**要等当前这一轮到达阈值并触发检查后**，才把该 AI 的阈值改为 **6**；之后是 7 次 AI 思考、`7 × 41 = 287` 次主更新。它不是立即把当前倒计时从 70 改成 6。
- 34 关开局玩家对象数（含建筑）均 ≥6，所以按该计数口径开局阈值全部是 70；之后玩家对象被打到 <6 也要在下一轮触发时才切换到 6。

### 5.4 等待门槛（最容易误读的地方）

`FUN_00471600` 的实际条件（0x00471600，反编译行 77540–77544）：

```c
if (AI_HQ_level < AI_gate
    && (player_HQ_level < player_gate - 1 || player_gold < 15000))
    return;   // 本次不进攻，计数已归零
```

变量映射：

| 代码变量 | 含义 |
|---|---|
| `DAT_004b8d29[AI]` | AI 升级等级字节（0 基；0 = 未升级） |
| `DAT_005d1e00[missionId]` | AI 的 `init[1]` 门槛（由当前关卡的 AI 写入按关卡号槽位） |
| `DAT_004b8d29[player]` | 玩家大本营等级 |
| `DAT_004b8cc0[player]` | 玩家的 `init[1]` 门槛 |
| `DAT_004b8d08[player]` | 玩家金（不是 AI 金；AI 金每次思考被覆写为 20000） |

因此等待不是“AI 等自己有钱”，而是**要求玩家发展到门槛，或者玩家金达到 15000**。`init[1]=1` 的 AI 在 1 级大本营时不会因等级条件等待；`init[1]≥2` 的 AI 才会进入等待分支。
