# 原版《赤壁》士兵移动与动画操作

> 目标：解释原版士兵为什么“流畅”，以及 `CB.EXE` 如何把 **UNIT.LWC 帧 + ANISEQ 方向/动作表 + 地图格 + 像素偏移** 组合成移动。  
> 方法：REA/Ghidra 静态分析 + `DATA.EXP` / `UNIT.EXP` / `ANISEQ01/02` 解码 + `UNIT.LWC` 原图提取。  
> **口径**：只以原版代码/数据为准；重制差异只作为后期修复对照，见 §8。

## 0. 结论先行

原版的“流畅”不是某个缓动函数，而是四件事叠加：

1. **更新频率高**：主循环按设置的目标间隔反复调用更新（`FUN_00454280` / `FUN_0045AFE0`），不是固定 1/30 s；设置值为 20/30/50/100 ms，另可能受 15 ms 限速影响。
2. **位置是“格坐标 + 格内像素偏移”**：单位同时维护 `+0x1A/+0x1C`（格）和 `+0x2C/+0x30`（带符号像素偏移）。渲染时由 `FUN_0045A6F0` 直接合成屏幕矩形，**不先把单位吸到格心再画**。
3. **动画帧与移动解耦**：移动处理器 `FUN_0045B910` 每次更新推进路径/偏移；动画帧由 `+0x6C & 1` 控制，**每 2 次更新推进 1 帧**。基础 30 ms 设置、未加 15 ms 限速时约 60 ms/帧；加限速则约 90 ms/帧。
4. **朝向与路径分开**：`+0x18` 是路径方向，`+0x16` 是显示朝向；`turn` / `walk` 是两套方向帧。转向不是每 tick 直接把 walk 方向掰过去，而是保留独立的转向帧时间。

> 重要订正：`DATA.EXP` 的 v8 常被 docs 叫“速度”，但原版动作/修理代码用 `1000 / v8` 计算动作周期；移动处理器 `FUN_0045B910` 没有引用 v8。**不要把 v8 当 px/s 移动速度**。

## 1. 主循环：更新时间从哪里来

证据：`FUN_00454280`（主战斗帧）→ `FUN_0045AFE0`（AI/单位更新入口）→ `FUN_0045B4E0`（逐单位模式分派）。

主循环（`WinMain` 内的战斗循环）使用：

```c
if ((DAT_004b8b54 + iVar1) <= now - last_update) {
    FUN_00454280();
    ...
}
```

- `DAT_004b8b54` 是游戏速度设置，初始化值来自 100/50/30/20 ms；
- 当 `DAT_00484BD8 == 0` 时 `iVar1 = 15`，相当于再加 15 ms 限速；否则为 0；
- 所以实际更新间隔是 `基础值 + (限速?15:0)`，取决于设置和机器，不是固定的 1/30 s；
- `FUN_0045B4E0(owner, slot)` 每次更新遍历每个单位，按 `+0x7C` 模式调用 `FUN_0045B910`（移动）等处理函数。

**对重制的意义**：重制 `SIM_DT = 1/30`，位置/方向只在 30 Hz 更新；原版在较快的设置下可以是 20–30 ms 级别，且逻辑更新与精灵帧有各自的时钟。

## 2. 位置模型：格 + 子格像素偏移

### 2.1 字段

单位记录（`0x174` 字节/单位）中的移动相关字段：

| 字段 | 含义 |
|---|---|
| `+0x1A` / `+0x1C` | 当前格坐标（ushort） |
| `+0x2C` / `+0x30` | 格内像素偏移（有符号 int） |
| `+0x3C` / `+0x3E` | 旧格坐标；碰撞回滚/转向用 |
| `+0x40` / `+0x44` | 旧像素偏移 |
| `+0x130` | 路径索引 |
| `+0xB0…+0x12F` | 路径方向字节块（32 个 dword） |
| `+0x6C` | 移动/动画更新计数器 |
| `+0x38` | 移动状态/转向分支 |

### 2.2 渲染

`FUN_0045A6F0` 从单位子结构取：

```text
screen_x = cell_x × tileW + (+0x2C 像素偏移)
screen_y = cell_y × tileH + (+0x30 像素偏移)
```

并加上精灵自身的锚点/偏移。它不是“先对齐格心，再显示”；每个更新都可以改变子格偏移，所以屏幕上看到的是**连续的小步位移**，而不是一格一跳。

> 证据：`FUN_0045A6F0` · `ev_2f9ca146…`。

## 3. 移动处理器 `FUN_0045B910`

### 3.1 路径

移动命令先由路径查找 `FUN_00441360` 生成路径，复制到单位 `+0xB0` 起的方向字节块，`+0x130` 置 0。移动处理器逐次消费路径方向：

- 方向字节包括普通方向以及 `8 / 9 / 13` 特殊字节；
- 遇到特殊字节时，`FUN_0045B910` 做路径节点切换/转向状态处理；
- 碰撞/无法继续时，把 `+0x1A/+0x1C`、`+0x2C/+0x30` 恢复到 `+0x3C/+0x3E`、`+0x40/+0x44` 保存的旧位置。

### 3.2 每次更新做什么

`FUN_0045B910` 的核心顺序（按代码行为概括）：

1. 若当前像素偏移为 0，读取下一个路径方向，更新 `+0x18` 路径方向；
2. 根据方向查 `DAT_005ABA40/44` 表，更新格坐标/子格偏移；
3. 按 `+0x2C/+0x30` 的偏移与方向，修正 `+0x34` 的渲染/步进量；
4. 用 `FUN_00442CA0` 做阻挡/通行检查；失败则回滚旧格/旧偏移；
5. 根据 `+0x38` 状态（8/9/0）选择转向/行走分支；
6. 最后用 `+0x14/+0x16` 计算 `+0x22` 绝对精灵帧，并清 `+0x24/+0x25` 帧计时。

这不是“每 tick 重算一个格子中心”，而是**路径步 + 子格偏移 + 旧位置回滚**。

### 3.3 速度

`FUN_0045B910` 中**没有** `DAT_004AF58F`（v8）的引用。移动的推进由路径/更新循环决定；v8 只在动作/攻击/修理代码中用于 `1000/rate` 周期。

> 因此，不能把 `DATA.EXP` 的“速率”列直接当移动速度。原版不同兵种看起来速度不同，可能来自路径/动画帧数/动作状态，而不是简单 px/s。

## 4. 动画：每 2 次更新推进一帧

### 4.1 帧选择

单位有三个关键字段：

| 字段 | 含义 |
|---|---|
| `+0x14` | 当前动画帧索引 |
| `+0x16` | 当前显示方向（0–7） |
| `+0x22` | 最终绝对精灵帧 |
| `+0x18` | 路径方向（用于选方向） |

帧表：

```text
absolute_frame =
   DAT_0052F108[type]
 + DAT_0052F10C[type][direction][frame]
```

帧数表：

```text
DAT_0052F048[type][direction] = 该方向的动作帧数
```

### 4.2 帧时钟

`FUN_0045B910` 在更新末尾：

```c
if (DAT_0052F048[type][dir] != 0 && (unit[0x6C] & 1) != 0)
    unit[0x14] = (unit[0x14] + 1) % DAT_0052F048[type][dir];
unit[0x22] = base_frame + frame_table[type][dir][unit[0x14]];
```

- `+0x6C` 每更新一次 +1；
- 只有**奇数**更新推进动画帧 → **2 次更新/帧**；
- 所有方向共用同一帧时钟；方向变了只换 `+0x16` 和帧表的列，不改变时钟；
- 这样即使位置每次更新只移动很小一段，动画也保持自己的节奏，不会每走一格就重置到第 0 帧。

### 4.3 不同单位的帧数

ANISEQ01 解出的行走帧数并不是全是 4：

| 类型 | walk 帧数/方向 | turn 帧数/方向 |
|---|---:|---:|
| 工人 30 | 5 | 4 |
| 步兵 32 / 38 | 4 | 4 |
| 骑兵 36 / 37 | 4 | 4 |
| 弓兵 45 | 5 | 4 |
| 车兵 34 | 4 | 4 |
| 500/1000 大编制 40–44 | 12–18 | 4 |

大编制单位的行走帧数明显更多，因此原版用**单位类型帧表**决定一轮 walk 的长度，而不是固定 4 帧。

## 5. 转向：`turn` 与 `walk` 分开

- `+0x18` 是路径方向，`+0x16` 是显示朝向；
- 移动开始/路径节点切换时，`FUN_0045B910` 会写入 `+0x38` 的 8/9/0 分支；
- ANISEQ 数据中每个方向都有 `turn`（4 帧）与 `walk`（4–18 帧）两套；
- 原地待命/开始移动时先走 `turn` 帧，进入移动后走 `walk` 帧；
- 面向目标时 `FUN_00421390` 用**实际屏幕向量**计算 8 方向（不是格坐标差值），再通过 `turn` 帧平滑到该方向。

> 说明：“移动开始先走 turn”是从 `+0x38` 分支与两套帧表推断的高置信模型；具体哪一节点用哪一帧仍需原版运行截图/逐帧轨迹核对（见 §10）。

> 重制当前在移动中直接把 `u.dir` 设为当前路段的 8 方向并立即用 `walk` 帧；没有原版“转向帧”那一段时间，所以转向看起来是瞬移式的。

## 6. 原版与重制的关键差异

| 项 | 原版 | 重制当前 | 后果 |
|---|---|---|---|
| 更新频率 | 设置 20/30/50/100 ms（另可能 +15 ms） | `SIM_DT=1/30` 固定 30 Hz | 位置/方向更新更粗 |
| 位置 | 格 + 子格像素偏移，`FUN_0045A6F0` 直接合成 | 像素 `ax/ay` + 格心路点 | 观感更“格子化” |
| 行走帧 | 每 2 次更新推进；帧数由 ANISEQ 表 | `step = anim*10`，固定 10 帧/秒 | 约 100 ms/帧；原版 40–90 ms/帧（取决于设置/限速） |
| 转向 | 路径方向/朝向分离，有 turn 帧 | 移动中直接按路段角度切 walk | 转向无过渡 |
| v8 “速率” | 动作/攻击/修理周期 `1000/rate` | `_rate_of`/`frame_sec` 仍按动作口径，但移动另用固定 `SPEED=110` | 不能把 v8 当移动速度 |
| 帧表 | 每类型、每方向独立帧数 | 图集帧 + clips 表；walk 被固定步进覆盖 | 大编制/弓兵等节奏不匹配 |

重制侧证据：

- `main.gd:114` `SIM_DT := 1.0 / 30.0`
- `main.gd:26` `SPEED := 110.0`
- `main.gd:3388/3718` `move_toward(..., SPEED * _spd_mult(u) * SIM_DT)`
- `battle_view.gd:2845` `step = int(u.anim * 10.0 * _spd_mult(u))`
- `battle_view.gd:2835–2840` 移动中直接 `clip = "walk"`；`turn` 只在非移动/攻击等分支使用
- `main.gd:776` `frame_sec = max(0.05, (1000/rate)*0.02)`

## 7. 重建建议

如果后续要修重制，按这个顺序：

1. **把移动/动画时钟拆开**：位置按原版更新节奏推进；动画帧每 2 次逻辑更新推进一次，或至少改成约 40–90 ms/帧，而不是固定 10 帧/秒。
2. **给每个类型/方向使用自己的 walk 帧数**：读取 `DAT_0052F048`/`ANISEQ` 的每方向帧数；不要把所有单位硬编码成 4 帧。
3. **恢复 turn 过渡**：方向变化先走 `turn` 帧，再进入 `walk`；转向不能在同一 tick 直接完成。
4. **保留子格偏移**：位置插值应覆盖 `cell + offset` 两个量；渲染每帧直接使用合成坐标。
5. **不要用 v8 驱动移动位移**：v8 是动作/攻击/修理速率；移动速度应来自原版路径/更新模型，或另行标定。
6. **先修行走，再修攻击**：攻击/修理的 1000/rate 周期是另一套，不能和走路帧混用。
